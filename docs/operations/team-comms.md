# Team Comms: both teams' TeamSpeak, per person, delayed

What this is for: the owner's brief, [docs/specs/team-comms-brief.md](../specs/team-comms-brief.md). The decision records: ADR-065 (capture, bridge, buffers, mixes), ADR-066 (on air: the public listen-in, NDI outputs, preview, ducking, overlay), ADR-068 (the dedicated recording, its speaker strip, calibration against the gameplay) and ADR-069 (phase 5: reconnects and failure recovery, the plugin remembering the team tabs, event presets, the plugin offered from the program, the setup checklist, the timing test) in [decisions.md](../architecture/decisions.md).

This document covers **phases 1 to 5** of the brief's delivery order: the feasibility checks with real evidence (phase 1); the base in the engine, i.e. the bridge to TeamSpeak, identities, timestamped per-person buffers and the mixes (phase 2); the public side (phase 3): one output-state controller for the public listen-in (Listen In — [team], End Listen-In, Mute All Comms), the public and recording mixes leaving the engine as NDI audio-only sources for OBS, the operator's private preview in their headphones, caster ducking, the team-only TEAM COMMS overlay, the **Team Comms** page and compact controls in Live Control, and the OBS setup with its routing checks; and the dedicated recording (phase 4): OBS's Source Record on a recording-only scene that MatchFrame sets up (gameplay, HUD, speaker strip, recording comms), its own Start/Stop, team, levels, folder and status, the recording-only speaker strip from the owner's reference, and the delay's calibration against the observer's gameplay; and phase 5: reconnects and failure recovery checked against the brief's acceptance rows, the plugin remembering the team tabs across a TeamSpeak restart, event presets, the TeamSpeak plugin offered from the program with a guided setup checklist, the recording's timing test, and a long soak with real TeamSpeak. What only the owner's PC can show is listed at the end, with a checklist to run there.

## How it works

```
TeamSpeak 3 client (owner's PC)                    MatchFrame engine
 tab "Team A" ─┐  playback thread                   ┌─ bridge 127.0.0.1:37213 (token)
 tab "Team B" ─┤  onEditPlaybackVoiceDataEvent ──►  │   per plugin: clock map (pings), counters
               │   copy → lock-free queue, zero     │
               │  sender thread ── TCP ───────────► ├─ slots A/B = match's team A/B (by team id)
               │   identity, stamp, events, stats   ├─ people: team/server/identity, saved choices
               │  ◄── MANAGE / RECORDING / PING ─── ├─ VoiceBuffer per person (sparse chunks, 48 kHz)
               └─ mic off, sound silent here        └─ mixer every 10 ms at now − delay:
                                                        public · recording · preview (+ activity)
```

**The plugin** (`native/ts3-matchframe-plugin`, C++17, one DLL/.so):

- **TeamSpeak's playback thread** calls `ts3plugin_onEditPlaybackVoiceDataEvent(schid, clientID, samples, sampleCount, channels)` once per talking person per block, before TeamSpeak mixes them. On a tab MatchFrame manages, the block is copied into a bounded lock-free queue (1 024 frames of up to 4 096 samples; a full queue drops the block and counts it, the callback never waits), then zeroed: the tab plays nothing on this computer. `onEditMixedPlaybackVoiceDataEvent` zeroes the tab's mix too (TeamSpeak's own sounds), and `onEditCapturedVoiceDataEvent` stops anything the listener might send.
- **TeamSpeak's main thread** (connection, move, nickname, talking events) keeps an identity cache and queues events; the queue never touches the audio thread.
- **The sender thread** reads `<data folder>/team-comms/bridge.json` (port and token, written by the engine), connects to 127.0.0.1, sends HELLO, each block with the speaker's `CLIENT_UNIQUE_IDENTIFIER`, the tab, the listener's own client id and the plugin's monotonic time (QueryPerformanceCounter / CLOCK_MONOTONIC), events, statistics each second; it applies MatchFrame's commands. It reconnects with back-off. While MatchFrame is away it drops audio (there is nothing to keep it for) and keeps tabs muted and silent.
- **Nothing is captured** until the engine says which tabs are the teams' (MANAGE). A tab that reconnects is captured again only after MatchFrame checks it is still in the team's channel. A whisper or anyone outside the tab's own channel is dropped.
- **Listen-only:** `CLIENT_INPUT_DEACTIVATED` and `CLIENT_INPUT_MUTED` (others see the listener muted); re-applied if someone switches the microphone back on in that tab. Never `CLIENT_OUTPUT_MUTED` (deafening would stop the callbacks).
- **Recording status:** `startVoiceRecording` / `stopVoiceRecording` on the managed tabs when MatchFrame signals recording (phase 4 ties it to the dedicated recording).

**The wire** (`services/local-engine/src/comms/wire.ts` has the layout): 12-byte header `MFTC`, version 1, type, length (≤ 1 MiB); JSON for HELLO/EVENT/STATS, binary for AUDIO (40-byte header, identity, int16 samples) and the engine's commands. Validated: format (int16 only), rate (8–48 kHz list), channels (1–2), frames, exact length, identity. TCP on 127.0.0.1 (not a named pipe) because Node and both platforms handle it the same and it tests the same here as on Windows; the token and the loopback-only listen (any other peer refused) protect it.

**The engine** (`services/local-engine/src/comms/`):

- `bridge.ts`: the TCP server. HELLO with the token within 3 s or ERROR and close; at most 4 plugins; at most 64 KiB before HELLO; a framing error closes, a bad message is dropped, counted and named; pings each second to map the clock.
- `clock.ts`: the plugin's µs onto the engine's ms: the answer with the shortest round trip of the last 10 s; small moves slewed (1 ms/s), jumps over 20 ms taken at once and counted; drift in ppm; before the first ping, the audio's own arrival bounds it.
- `buffer.ts`: one `VoiceBuffer` per person: sparse chunks (one per TeamSpeak block) at their place on the timeline; a block within 20 ms of the previous end continues it sample for sample; a pause starts a new chunk; a clock jump back of more than 200 ms cuts and re-lays; samples the outputs already played are dropped as late; other rates converted (linear, continuous), stereo to mono; trimmed to the delay + 2 s; all buffers together capped (512 MB default) by dropping the oldest audio, which makes that team "not ready" until the playhead passes it.
- `mixer.ts`: every 10 ms block at the playhead (output time − delay): **public** (silent unless one team is open; switching closes the old team to silence over 40 ms before opening the other), **recording** (its own team, independent), **preview** (soloed people). Inclusion and level are gains after the buffers, ramped over 10 ms: unchecking removes buffered speech from the next block. A team not ready at the playhead contributes nothing. Activity per person per output from the samples mixed (attack 15 ms, release 250 ms, speaking above −45 dBFS); the public output reports team level only. `CommsSink` is the interface the phase 3 outputs plug into.
- `service.ts` (`TeamComms`): slots, tabs, people, readiness, delay changes (fade out on the old playhead, then the new one, readiness checked again), the public gate closing itself when its team's source is lost (a new Listen In is needed), diagnostics.
- Routes: `GET /api/v1/comms`, `PUT /api/v1/comms/settings`, `PUT /api/v1/comms/slots/:slot` (passwords to the secret store), `PUT /api/v1/comms/participants/:key`, `POST /api/v1/comms/bridge/rotate-token`.

**On air (phase 3, `comms/controller.ts`, `outputs.ts`, `ndi-worker.ts`, `preview.ts`, `ducking.ts`, `overlay.ts`, `public.ts`):**

- **One output-state controller** (`ListenInController`) is the only thing that moves the public gate. *Listen In — [team]* (by the match's team id: halftime changes nothing) refuses unless Team Comms is on, the public output runs and that team's buffer holds the delay at the playhead (the button says why, e.g. "ready in about 42 s"); it closes the other team through silence first. *End Listen-In* closes it (40 ms). *Mute All Comms* closes it in 5 ms (no click) and leaves the recording and the preview alone. A lost source, a bridge or slot reset, the active match changing or the public output stopping closes it as **FAULT**, silent, until an explicit new Listen In (End Listen-In acknowledges it). A delay change while on air is **BUFFERING** (silent) until the longer delay is held, then on air again (the operator's Listen In stands; nothing was reset). Nothing about the listen-in is saved: every start is OFF. Recording and preview never call into it.
- **Outputs** (`CommsOutputs`): every 10 ms block of the public mix is checked once more before it leaves: while the gate is closed the block sent is zeros, whatever the mix holds. Public and recording blocks go, with their place on the engine's timeline, to the **NDI process** (forked like the replay feed's; the NDI binding loads only there): two audio-only senders, "MatchFrame Comms" and "MatchFrame Comms Recording", 48 kHz stereo 32-bit float (FLTp, the mix on both channels), 480-sample frames, each sent a fixed 60 ms after its own time on MatchFrame's clock and stamped with that time as its NDI timecode. A block that isn't there in time goes as silence (and is dropped when it comes: never stale or repeated audio); a stalled process skips ahead. If the process stops, a listen-in closes (FAULT) and the process starts again after 3 s.
- **Preview:** the preview mix (the people soloed) goes over `/api/v1/comms/preview/ws` (operator token, production roles only) as 20 ms chunks of 16-bit samples with their timeline place; the console schedules them back to back with Web Audio on the output device picked (`AudioContext.setSinkId`, or an audio element's), 120 ms ahead, never more than 600 ms. Never NDI, never OBS.
- **Caster ducking** (`CommsDucking`): as a listen-in opens, the OBS inputs picked as the casters go down by the amount set (default −10 dB, 300 ms ramp), their volumes saved first (`comms.duck` in the engine's settings); as it closes (End, Mute All, a fault) they go back exactly, unless moved by hand meanwhile (then left alone), or the replays hold the same input (then left at the replays' level; they restore it). The replays' ducking (`replay/audio.ts`) asks the same of Team Comms (`DuckPeer`), so whichever ends last puts the volume back. Left down by a crash: put back at the next start, once OBS answers.
- **Overlay** (`CommsOverlay`): `/comms/public?t=<token>` on the overlay server (its script `/comms/public.js`; the overlay server allows no inline script), state over `/comms-ws`: `{type, v, onAir, team: {name, shortName, logoUrl, color}, label: "TEAM COMMS", placement}` and nothing else, ever. The page hides the banner whenever the engine isn't there.
- **Routes:** `POST /api/v1/comms/listen-in {teamId}`, `POST /api/v1/comms/listen-in/end`, `POST /api/v1/comms/mute-all`, `PUT /api/v1/comms/public` (NDI output, ducking, banner placement), `GET /api/v1/comms/obs/inputs`, `GET /api/v1/comms/obs/check`, `POST /api/v1/comms/overlay/obs`; `GET /api/v1/comms` carries the on-air state under `onAir`. Every action is in the audit log.

**The dedicated recording (phase 4, `comms/recording.ts`, `strip.ts`, `calibrate.ts`):**

- **The scene** "MatchFrame Comms Recording Scene" (an OBS set up by 0.11.0 or earlier keeps its "Matchframe Comms Recording") is built by **Team Comms → Dedicated comms recording → Set up the recording scene in OBS**: the live scene's gameplay source (the game capture: the same source, shared, as OBS's Add → Existing, with its transform there) and its MatchFrame HUD browser source (shared), the speaker strip's browser source "MatchFrame Speaker Strip" (1920×1080, on top), DistroAV's NDI source "MatchFrame Comms Recording" (audio only, kept receiving), and "MatchFrame Recording Game Audio", a copy of the live scene's game audio input (Application Audio Capture of CS2) whose fader is the recording's game level. The recording's two audio inputs are put on track 1 only and not monitored. Source Record's filter "MatchFrame Recorder" (kind `source_record_filter`) goes on the scene, stopped. Existing sources are shared, never replaced; running it again brings the scene up to date. MatchFrame guesses the gameplay (a Game Capture), the HUD (a browser source on MatchFrame's overlay server) and the game audio (an application capture of cs2.exe); the console lets the operator choose.
- **Start/Stop** set the filter's record mode (Always / None) with its settings: the folder, the file name "MatchFrame Comms <team> <date> <time>", the format (MKV by default: a crash leaves a playable file; OBS remuxes it to MP4), the encoder (by default OBS's own recording encoder, as Source Record picks it: NVENC on an NVIDIA PC), bitrate, split files, and the scene's own sound (Source Record's default). TeamSpeak's recording indicator comes on at Start and goes off at Stop. Nothing about the public listen-in touches it: Mute All Comms closes only the public route.
- **Status, every second:** elapsed time, the file Source Record writes (found in the folder by its name, and its growth), free space on the drive (a warning under 20 GB, a fault under 2 GB), whether OBS mixes track 1 (below), whether DistroAV receives "MatchFrame Comms Recording", and faults: the filter stopped or removed in OBS, no file, a file that stopped growing. After an engine restart a recording still running in OBS is carried on (never started by MatchFrame by itself).
- **The recording team** is a team id (never CT/T). Changing it changes the recording mix (the old team fades to silence, then the new one, 10 ms) and the strip's cards on the same block. **Comms level** is MatchFrame's gain on the recording mix before NDI (ramped over a block; −60 dB is off and the strip lights nobody); **game level** is the game audio copy's fader in OBS.
- **The speaker strip** (`/comms/recording?t=<its own token>` on the overlay server, its script `/comms/recording.js`, its socket `/comms-rec-ws`): the recording team's people with Include in Recording, at most seven, in roster order (mapped players by the team's roster, then the rest as first seen); each a clipped-corner hexagon with rounded corners, a substantial frame and a dark inset, the portrait grayscale with a grey frame while silent and in colour with a green frame (#20FF00, configurable) while speaking. Pictures: the roster player's own (unless the player hides their photo), else the HUD images' default player picture for that player's place, else the operator's placeholder, else MatchFrame's silhouette; a crop per portrait (the point kept in view and a zoom). Speaking comes from the recording mix's per-person activity (`MixBlock.activity.recording`: the samples actually mixed, after the delay, inclusion and level), with the strip's own attack (30 ms) and release (350 ms): everyone active lights during overlapping speech; nothing lights from TeamSpeak's talk events. Each block's cards and speakers are sent when that block leaves for OBS (its output time plus the NDI send latency) plus a timing offset the operator calibrates. The page receives card ids (not TeamSpeak identities), names, picture addresses, crops and the layout; the public overlay receives none of it (its own route, token and payload, unchanged).
- **Calibration** (`comms/calibrate.ts`): below.

**Reconnects, failures, presets and setup (phase 5, `comms/presets.ts`, `setup.ts`, `timing-test.ts`; ADR-069):**

- **Who is who survives every reconnect.** A person is their TeamSpeak unique identity, which travels with every block of their voice; session ids are only looked up. The engine takes a block only from someone its tab's channel holds now (else it is dropped and counted as `notInChannel` on the tab): a block from before the listener's tab moved, or from someone who just left, never lands on another team or person. The plugin remembers who left its channel for 5 s, so a block captured before they left keeps their name even when TeamSpeak has already given their session id to a newcomer, and it names a person it hadn't seen ahead of their first block. A restarted TeamSpeak may connect the tabs in another order (other `schid`s): the teams follow the channels. Newcomers, also with a known nickname, stay excluded.
- **Nothing reopens the public listen-in by itself:** Listen In needs the team's TeamSpeak tab captured now (its buffered audio from before a loss doesn't count); every loss (TeamSpeak restarted or frozen, a tab disconnected or moved, the bridge, the NDI process) is FAULT and silence until an explicit Listen In; MatchFrame restarting starts OFF. The recording plays out what it had buffered, then silence, and comes back only when the new capture is a full delay old (never fresh audio).
- **Restart in either order.** The plugin re-reads the bridge file on each attempt (MatchFrame's new port and token) and reconnects with a back-off; MatchFrame started first waits for it. **A frozen TeamSpeak** (connection open, nothing sent) is closed after 6 s without a message, counted on the computer's clock; when MatchFrame itself didn't run for a while (the computer froze or slept), that time doesn't count against the plugins.
- **The plugin remembers the team tabs** in TeamSpeak's own config folder (`%APPDATA%\TS3Client\matchframe_comms_tabs.txt` on Windows: server unique id, channel name and the address TeamSpeak dials, at most four). While team tabs are remembered, any TeamSpeak connection the plugin hasn't settled yet is silent here from its first block, decided in the audio callback itself (measured below: under load TeamSpeak's playback starts on a new connection before its main thread even reports it connecting, and it can say "established" before the channel can be read); once its channel is known it is settled: in a remembered team channel listen-only and silent here before MatchFrame answers (and even with MatchFrame closed), in any other channel TeamSpeak's own (it plays); on a team's server a new connection first lands in the server's default channel and is moved on a moment later, so there it stays silent for its first 3 s before being released. It is captured only once MatchFrame asks. A remembered tab whose server and channel are no team's now is handed back to TeamSpeak and forgotten, once TeamSpeak has reported both (its first report of a new connection can come before the server's address is filled in). The Team Comms page lists every TeamSpeak tab and which team it is (or "Not a team tab"). **To use a team channel in TeamSpeak normally again without MatchFrame** (microphone and sound back): close TeamSpeak and delete `matchframe_comms_tabs.txt`, or turn the plugin off in TeamSpeak (Tools → Options → Addons → MatchFrame Team Comms → Disable).
- **The NDI process** restarts 3 s after it stops, then 6, 12, 24, at most 30 s while it keeps stopping soon after a start, back to 3 s after a minute of running; the page shows the restarts, the last exit and the next start. While it is down nothing reaches OBS: the public route is silent (FAULT) and the dedicated recording shows **RECORDING FAULT** (gameplay without comms).
- **OBS** going away while recording is **RECORDING FAULT** (MatchFrame can't confirm the file); when OBS answers again and Source Record still records (or records again into a new file by itself, with its saved Always mode), the fault clears and the newest file is followed; if Source Record stopped, the fault says so and **Start Recording** makes a new file. Caster ducking goes down again when OBS comes back during a listen-in (from the saved volumes) and back up once OBS answers if the listen-in ended meanwhile.
- **Event presets** save, under a name and the active match's event, the people (mapping, display name, Include in Broadcast, Include in Recording, level), each team slot's TeamSpeak server, port, channel and listener names, the delay, the recording team and its levels, the speaker strip and the on-air settings. Never the listen-in (loading never opens or closes it), the operator's Solo, passwords or tokens (per slot, in the secure settings), the recording folder or file format.
- **Setup:** *Install TeamSpeak plugin* copies the program's build (`resources\ts3-plugin`) into TeamSpeak 3's plugins folder; the checklist reads its five steps live (TeamSpeak plugin, DistroAV, Source Record, OBS scenes, calibration).
- **Timing test:** five 3 150 Hz beeps, 200 ms each, a second apart, in the recording output only, with every strip card lit on exactly the same blocks; found in the finished file (below).

**Readiness, exactly:** a team is ready at the playhead when its tab has been captured without a break since before the playhead (and no audio before it was trimmed or dropped). After a (re)connection that is once the delay has passed. After a loss, the audio captured before it still plays out for the delay (it is real, delayed audio), then the gap is silence, then it resumes. The **public** listen-in does not wait for that: it closes at the loss.

**Delay:** 0–300 s plus −999…+999 ms, never less than 150 ms (the plugin-to-engine transport; measured p99 5 ms). The delay is measured from the moment TeamSpeak hands the block to playback, on the engine's clock. It is calibrated against the observer's gameplay as OBS shows it (Calibration, below).

## Setup

### TeamSpeak and MatchFrame

1. **Install the plugin:** close TeamSpeak 3, then **Live Control → Team Comms → Setup checklist → Install TeamSpeak plugin** (it copies the program's build into `%APPDATA%\TS3Client\plugins\`; refused while TeamSpeak runs, because TeamSpeak holds the file). By hand: *Show the plugin package* and double-click `matchframe-team-comms.ts3_plugin` (TeamSpeak's add-on installer), or *Open TeamSpeak's plugins folder* and copy the DLL there. Start TeamSpeak: Tools → Options → Add-ons: *MatchFrame Team Comms* enabled. (A program built without the plugin says so: `plugin.json` has `built: false`; build it as below.)
2. In TeamSpeak, connect a tab to each team's channel: **Connect in TeamSpeak** under each team (Team Comms → Bridge and TeamSpeak plugin) hands the team's link (`ts3server://…`: server, port, listener nickname, channel; no password in it, TeamSpeak asks) to TeamSpeak; or Copy link into a bookmark per team with *Connect on startup*. If TeamSpeak opens the second link in the tab of the first, use File → Connect in a new tab with the copied link (TeamSpeak decides; not tested on Windows). **On a default server each identity can be connected once:** give the second tab its own identity (Tools → Identities → Add, then pick it in the bookmark) or ask the server admin to allow two connections per identity (`i_client_max_clones_uid`). Two TeamSpeak clients, one per team, work too. The plugin remembers the team tabs: after a TeamSpeak restart they are listen-only and silent here at once, before MatchFrame answers.
3. In MatchFrame: activate the match (its team A and team B are the slots). **Live Control → Team Comms → Bridge and TeamSpeak plugin:** Team Comms on; each team's server address, port and channel (passwords go to MatchFrame's secure settings and are never shown again; the bridge token is never shown either: the plugin reads it from the bridge file; *Rotate token* makes a new one).
4. MatchFrame writes `%APPDATA%\MatchFrame Esports\team-comms\bridge.json`; the plugin finds it, connects, and MatchFrame takes over the two tabs (muted, silent, captured). Each team panel shows its TeamSpeak tab, the listener (microphone off, not deafened), readiness and everyone in the channel, **excluded until you include them** (Include in Broadcast, Include in Recording), with a level, a roster player to map them to, a live (incoming) meter, a delayed meter (at the outputs' time) and Solo for your headphones.
5. **Delay:** seconds plus a fine adjustment in ms, shared by both teams (they play against the same gameplay). Start from the gameplay delay you use (the GOTV delay, e.g. 90 s), then calibrate it (below).
6. **Preview in your headphones:** pick the headphones (an output OBS doesn't capture), *Listen in headphones*, Solo someone. Only you hear it.
7. **Event presets** (Team Comms → Event presets): once the people are mapped and chosen, the delay calibrated and the recording team, strip and on-air settings set, *Save as* a name (it goes with the active match's event). Next time: *Load*. The badge says which preset is active and, if anything changed since, what (people and choices, TeamSpeak servers and channels, delay, recording team and levels, speaker strip, on-air settings); *Save “name”* keeps the changes. Loading never puts comms on air or takes them off; passwords and your Solo are never in a preset.
8. **Setup checklist** (top of the Team Comms page): TeamSpeak plugin, DistroAV, Source Record, OBS scenes, calibration, each *Done*, *To do* or *Not checked* from MatchFrame's own live checks, with the details of each.

### OBS (one PC)

MatchFrame sends the comms; OBS only receives them. Install **DistroAV** (the OBS plugin for NDI; 6.x, with the NDI 6 Runtime it asks for: MatchFrame's own NDI runtime is inside MatchFrame and isn't OBS's).

1. **Desktop Audio off:** Settings → Audio → Global Audio Devices → Desktop Audio: *Disabled* (and Desktop Audio 2). A desktop capture takes everything the PC plays: TeamSpeak's own sound if it ever played, the operator's preview, a second copy of the comms.
2. **Game audio as its own source** in the live scene: Add → Application Audio Capture → *[cs2.exe]: Counter-Strike 2*, named e.g. "Game audio".
3. **Casters as their own source(s):** Add → Audio Input Capture (a microphone, or the casters' mixer), named e.g. "Casters". In MatchFrame, **Team Comms → Caster ducking:** tick them, choose the amount (default −10 dB) and the ramp.
4. **Comms:** in the live scene, Add → *NDI™ Source*, named **MatchFrame Comms**; Source: *<this PC's name> (MatchFrame Comms)*; Bandwidth: *Audio only*. Then Advanced Audio Properties → MatchFrame Comms → Audio Monitoring: **Monitor Off**; tracks: the stream's. Add the same source (Add → Existing) to any other program scene in which a listen-in may continue. Its silence when no listen-in is open is MatchFrame's (zeros are sent): don't rely on muting it in OBS, and don't leave it muted either.
5. **Team-only graphic:** **Team Comms → Public Team Comms graphic → Add to the live scene in OBS** (a 1920×1080 browser source "MatchFrame Team Comms" on top of the live scene; its position under the scorebar or near the bottom, set there).
6. **Recording comms:** *<this PC's name> (MatchFrame Comms Recording)* is for the dedicated recording's own scene only (the setup below makes it). **Never in a program scene.**
7. **Team Comms → OBS routing check:** Desktop Audio off, MatchFrame Comms in the live scene and not monitored, the recording source off the program, no capture of TeamSpeak itself, the caster inputs present. Then the listening tests below.

Never add a capture of TeamSpeak (Application Audio Capture of ts3client) or of MatchFrame's own window: comms reach OBS only as *MatchFrame Comms*.

### The dedicated comms recording (OBS, one PC)

**Install Source Record** (exeldro; free, GPL-2.0; MatchFrame doesn't bundle it): close OBS; download the build for your OBS (0.4.x for OBS 30 and 31) from https://obsproject.com/forum/resources/source-record.1285/; run its installer (or unzip it into OBS's folder, e.g. `C:\Program Files\obs-studio`); start OBS. MatchFrame checks for its filter kind `source_record_filter`; if OBS hasn't got it, the Team Comms page says so with these steps and Start Recording is refused.

1. **OBS → Settings → Video:** the canvas the recording gets (target 1920×1080 at 60 fps; Source Record records the scene at the canvas size and frame rate).
2. **OBS → Settings → Output:** the stream (or OBS's own recording) on **track 1** (Simple output always is; Advanced: Streaming → Audio Track 1). Source Record takes the recording scene's sound from track 1 and **OBS mixes track 1 only while an output uses it**: before the stream starts (and with no OBS recording or replay buffer running) the comms recording would be silent. MatchFrame shows "OBS track 1: NOT MIXED" and a fault while recording in that state.
3. **Live scene:** the game capture, the MatchFrame HUD browser source and the game audio as their own sources (Application Audio Capture of CS2; turn Game Capture's own *Capture Audio* off, or the game would be recorded twice). The casters stay in the program scenes only.
4. **Team Comms → Dedicated comms recording → Recording scene in OBS:** check the gameplay, HUD and game audio MatchFrame found (or choose them), then **Set up the recording scene in OBS**. Each step is listed (Done / Fix / Note): the scene "MatchFrame Comms Recording Scene" (never put it on program), gameplay and HUD shared from the live scene, "MatchFrame Speaker Strip" on top, "MatchFrame Comms Recording" (DistroAV; if DistroAV is missing it says so), "MatchFrame Recording Game Audio", nothing else with sound, the Source Record filter "MatchFrame Recorder".
5. **Folder** (Choose folder… is Storage's folder picker), **format**, **encoder** (NVENC next to the stream's encoder on an NVIDIA card), **bitrate** (16 Mb/s ≈ 7 GB an hour), **split** (optional).
6. **Recording team**, **game level**, **comms level**; **Start Recording**. Live Control has the state and Start/Stop too.
7. **Team Comms → OBS routing check** now also checks the speaker strip is not in the live scene.

**Track layout:**

| Track | What | Notes |
|---|---|---|
| OBS track 1 | The stream's (and OBS's own recording's) mix: whatever is on program (game audio, casters, *MatchFrame Comms*) | Also the track Source Record reads for each source of the recording scene. "MatchFrame Recording Game Audio" and "MatchFrame Comms Recording" are on track 1 only, but they are in no program scene, so they are never in the stream's mix |
| Tracks 2–6 | Not used by MatchFrame | Keep the recording's two inputs off them (a VOD or stem track of the program would otherwise not change, as they are not on program, but nothing needs them) |
| The comms recording's file | One stereo AAC track: the recording scene's own sound = game audio copy + recording comms | Casters excluded by not being in the scene. Separate game/comms stems are not possible with Source Record's scene sound (one track); its other audio modes record OBS's mixes of the program instead (measured below) |

### Calibration against the gameplay

The comms must play beside the gameplay as OBS shows it, which is the GOTV/observer delay plus the transport and capture of the picture, while the comms take a different path (TeamSpeak → MatchFrame → NDI → DistroAV). **Team Comms → Delay against the gameplay:**

1. Set the delay to the gameplay delay you use (e.g. 90 s) and let the buffers fill.
2. Choose the team, ask a player to say a short sharp "mark!" (or clap) **at the instant of something visible**: a shot, a flash popping, a jump. Press **Arm** just before. MatchFrame takes the start of that sound from the player's own TeamSpeak stream (the first sound after 300 ms of quiet, on the engine's clock, exact to TeamSpeak's 7.5 ms blocks).
3. Watch the observer's gameplay in OBS (program, preview or the recording scene). Press **Seen in gameplay** the moment it happens there.
4. Three to five marks. MatchFrame suggests the median less your reaction time (200 ms by default: an estimate, set your own) less the comms' path to OBS (the NDI send latency); the spread says how much to trust it. **Use this delay.**
5. **Timing test in a recording** (same panel): start the dedicated recording with at least one person included in it (the strip shows their card), press **Run timing test** (five beeps, 3 150 Hz, 200 ms, one a second, in the recording comms only, never on air, and every card of the strip lit on exactly the same 10 ms blocks), wait for them (about six seconds), **Stop Recording**, then **Find it in the recording**: MatchFrame reads the finished file with ffmpeg (the one Replays → Replay feed downloads), finds each beep's start in the sound and each flash's first frame in the strip's area of the picture, and says how far apart they are. **Apply the suggestion** sets the strip's timing offset (so the strip lights with the comms) and, when the delay in use is the one the marks suggested, the fine ms less what DistroAV and OBS add to the comms on their way in (taking the browser source to show the gameplay's frame: both are pictures captured by OBS). Only files of the dedicated recording (its folder) are read.
6. **Check by eye** (always worth doing once, and the way if the delay was set by hand): in a player that steps frames, the call and the moment in the gameplay should be within a frame or two; move the delay's fine ms by what is left (positive: comms later). Then a call's start against its card turning green: **Speaker strip → Timing offset** by the difference (positive: later).

A delay change mutes the outputs for a moment and re-buffers if it got longer; the recording keeps running.

### Listening tests: loopback, duplication, feedback (on the owner's PC)

The routing check reads OBS's lists; these listen to what actually goes out. Record the program in OBS while doing them, and play the recording back.

1. **Silence when off (loopback):** no listen-in (OFF), a team talking. OBS's *MatchFrame Comms* meter stays at −∞ and the program has no comms; the PC's speakers play nothing of TeamSpeak.
2. **Preview isolated:** Solo someone, listen in the headphones, still no listen-in: the headphones carry the voice, every OBS meter stays still. Then Listen In — the *other* team: the program carries only that team; the soloed person stays in the headphones only.
3. **Duplication:** Listen In; someone says a short sharp word. In the recording it is there once: no second copy 0–500 ms later (a desktop capture or audio monitoring would add one).
4. **Feedback:** during a listen-in with the casters quiet, the Casters meter stays at its noise floor (comms in the casters' headphones must not reach their microphones), and the comms carry no echo of the program.
5. **Team switch:** Listen In A, then Listen In B while both teams talk: no moment with both teams, no click.
6. **Mute All Comms** during speech: the program is silent at once; the dedicated recording carries on (its file keeps the comms).
7. **Restart:** close MatchFrame during a listen-in and start it again: comms come back OFF, the casters at their own volume.

## Building the plugin

The TeamSpeak 3 Client Plugin SDK headers are TeamSpeak's ("all rights reserved"); they are **not in this repository**. `scripts/fetch-sdk.mjs` downloads the 7 headers from https://github.com/TeamSpeak-Systems/ts3client-pluginsdk at commit `4aa90a5` (tag 26, plugin API 26) and checks each SHA-256 (`sdk.json`).

```
node native/ts3-matchframe-plugin/scripts/fetch-sdk.mjs              # NODE_USE_ENV_PROXY=1 behind a proxy
cmake -S native/ts3-matchframe-plugin -B build -A x64                # Windows, MSVC (what CI does)
cmake -S native/ts3-matchframe-plugin -B build -DCMAKE_BUILD_TYPE=Release                                    # Linux
cmake -S native/ts3-matchframe-plugin -B build -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-w64.cmake -DCMAKE_BUILD_TYPE=Release   # Windows DLL from Linux
cmake --build build --config Release
node native/ts3-matchframe-plugin/scripts/package.mjs build/Release/matchframe_comms_win64.dll   # → dist/*.ts3_plugin, plugin.json
```

`windows-program.yml` builds it with MSVC (static runtime), packs it, and the program ships it in `resources/ts3-plugin/` (`plugin.json` says `built: false` when it wasn't built; the step stays non-fatal until it is proven on the runner). The program offers it from Team Comms → Setup checklist → *Install TeamSpeak plugin* (it reads `MATCHFRAME_TS3_PLUGIN_DIR`, which the program sets to that folder). The same sources build with the Linux and mingw-w64 steps above (checked in phase 5: no warnings). The plugin keeps the team tabs it captured in `matchframe_comms_tabs.txt` in TeamSpeak's config folder (`getConfigPath`; `MATCHFRAME_COMMS_TABS_FILE` overrides it for tests): `MFTABS2`, then one line per tab, tab-separated: server unique id, channel name, address, port (an `MFTABS1` file of server and channel only is still read).

### What to test on your PC (a checklist, about an hour)

Before a match day, on the production PC, with the real TeamSpeak server and two people (or two spare PCs) talking in each team channel:

1. **TeamSpeak plugin:** close TeamSpeak 3; Team Comms → Setup checklist → *Install TeamSpeak plugin*; start TeamSpeak, enable *MatchFrame Team Comms* (Tools → Options → Add-ons). Connect both team tabs with the TeamSpeak links. The checklist's first step turns *Done*; the Bridge panel lists each TeamSpeak tab as Team A / Team B. On the server, both listeners show a muted microphone, not deafened. Nothing of the teams plays on the PC's speakers.
2. **TeamSpeak restart:** close TeamSpeak (or end it in Task Manager) during a listen-in: Team Comms shows FAULT and stays silent. Start TeamSpeak again *with MatchFrame closed*: the team tabs reconnect muted and silent on the PC (the plugin remembered them). Start MatchFrame: the tabs are captured again; Listen In works again only when you press it.
3. **DistroAV:** OBS → add the NDI sources as in the OBS setup; the checklist's DistroAV step shows a receiver on both. Listening tests 1–7 above (loopback, preview isolated, duplication, feedback, team switch, Mute All, restart).
4. **Headphones:** pick headphones OBS doesn't capture, Solo a player: only you hear them; every OBS meter stays still.
5. **Ducking:** during a listen-in the casters go down by the amount set and back exactly at End; move a fader during a listen-in: it is left as you put it. Restart OBS during a listen-in: the casters go down again when OBS is back.
6. **Source Record with NVENC:** set up the recording scene from MatchFrame, choose NVENC (or your GPU's encoder), record 10 minutes with the stream running: the file plays, the gameplay never leaves it while the program cuts, the excluded people are absent, the casters absent. Watch OBS's Stats (rendering lag, encoding lag, skipped frames) and Task Manager (GPU encoder, CPU, disk).
7. **Calibration:** marks (Delay against the gameplay), *Use this delay*; a one-minute recording with the timing test; *Find it in the recording*; *Apply*; check one call against the gameplay and its card by eye in the file.
8. **Presets:** *Save as* the event's name; change something; *Load* puts it back; the badge says what differs.
9. **Single-PC load:** CS2 (spectating), OBS streaming + Source Record, TeamSpeak with both tabs, MatchFrame with a listen-in and the recording, for 30 minutes: CPU, GPU, memory of each (Task Manager), OBS's skipped frames, MatchFrame's support file (Team Comms: drops, NDI lag and resyncs, buffer drops). If the Team Comms page shows NDI gaps or late blocks, raise the NDI latency (Outputs → Output settings) and calibrate again.
10. Send the support file (Settings → Support) and OBS's log of that session with what you saw.
